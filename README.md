A build-level SBOM generator for Ariel OS-based Rust projects.

## Goal

The goal of this project is to create/lay the groundwork for a build-specific SBOM generator for [Ariel OS](https://github.com/ariel-os/ariel-os) projects. Since the Cyber Resilience Act does not go into much detail in terms of SBOM requirements, right now the current [BSI technical guideline for SBOMs](https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/Publications/TechGuidelines/TR03183/BSI-TR-03183-2_v2_1_0.pdf) will instead be used as a reference and compliance for it be strived towards.

## Installation

If not done already, install the [build prerequisites](https://ariel-os.github.io/ariel-os/dev/docs/book/getting-started.html#installing-the-build-prerequisites) needed for Ariel OS.

Afterwards, simply clone this repository to a location of your choosing.

## Try it out

Generate an example SBOM for the Ariel OS `coap-client` example:

    cargo run --example ariel_os_example

Generate an example SBOM for a custom, [out-of-tree Ariel OS project](https://ariel-os.github.io/ariel-os/dev/docs/book/getting-started.html#starting-an-application-project-from-a-template-repository):

    cargo run --example custom_oot_project -- -r <PATH_TO_PROJECT> [-b <BUILDER>]

If your project of choice requires a specific [laze builder](https://ariel-os.github.io/ariel-os/dev/docs/book/hardware-functionality-support.html) other than `nrf52840dk`, it can be provided via the optional `-b` argument.

## Comparison

This section provides a short comparison of Rust component recognition based on the specific build for this tool and several existing SBOM tools. 

`cargo tree` is the baseline to that the tools are compared to, as it recreates the build-specific dependency graph and thus includes only crates that were compiled for the specific build and no superfluous ones.

False positives are components listed by a tool that are not present in the dependency graph generated by `cargo tree` and false negatives are components listed in the graph but not by the tool in question.

The project used is the [v0.4.0 Ariel OS CoAP test](https://github.com/ariel-os/ariel-os/tree/v0.4.0/tests/coap), but recreated as an out-of-tree project, and built for the nRF52840-DK board.

For more details, check [COMPARISON](https://github.com/Nerving/ArielOSBOM/blob/master/COMPARISON.md).

## Approach

Generates an SBOM of an Ariel OS project at the build-specific scope of the specified board(s) or last executed build. For every `--builder` argument supplied, the following steps lead to the generation of the SBOM(s):

1. The builder argument is supplied to [laze](https://github.com/kaspar030/laze) to generate the build command for the corresponding board.
2. The build command is read and parsed from the laze-generated `compile_commands.json` file. If no builders were supplied, the last executed build command is taken from `<PATH_TO_PROJECT>/build/build-local.ninja`.
3. Using the parsed environment variables and Rust features, [cargo tree](https://doc.rust-lang.org/cargo/commands/cargo-tree.html) is executed to obtain the dependency graph, indicating which crates are actually part of the specific build. 
4. Using the parsed Rust features, [cargo metadata](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html) is executed to obtain further information to enrich the SBOM. The `Cargo.lock` files at the project root and, if present, of the Ariel OS import additionally provide the package checksums for components taken from [crates.io](https://crates.io/).
5. All crates irrelevant to the build, determined by their lack of presence in the output generated by `cargo tree`, are filtered out of the `cargo metadata` output before all component information needed for the SBOM(s) is stored in a raw, intermediate representation.
6. Based on the given formats (CycloneDx 1.6/1.7, raw), SBOM(s) are generated and put into the output directory. 

## Curent State

### What the tool currently does provide

- build-level component recognition
    - Rust components
        - catalogues only all crates that are compiled during the building process
        - takes features and environment variables into account
    - information on
        - component dependencies (in the build-specific context)
        - name, version, license(s)\*, creator(s)\*, source repository link\*
        - crate hashes via Cargo.lock for crates from crates.io
- SBOM generation
    - at the project root level and also for other workspace members (e.g. tests/examples)
    - based on specified builders or the last executed build command
    - output formats
        - raw data format that is used during component aggregation
        - CycloneDX version 1.6, 1.7 (due to the limited fields, they are basically identical right now) 

### What the tool currently does not provide (yet)

- build-level component recognition
    - no component recognition outside of Rust/Cargo context
    - no alternative processing if cargo metadata fails
    - information marked with \* in the previous section if it is not provided by cargo metadata
    - information on
        - license information from LICENSE file(s) if present
        - crate features
        - additional component identifiers (purl, cpe, SWHID, ...)
- program metadata
    - intended device specifications, storage/memory footprint, supported features/protocls, ... (suggestions?)
- SBOM generation
    - output formats
        - any SPDX version
        - older CycloneDX versions
- (full BSI guideline compliance?)

## Usage

### Builder selection

Option 1 (explicit builder selection):
- provide the project's root path via the command line (`-r <PATH>`)
- provide the laze builder(s) for which you want to generate the SBOM(s) via the command line (`--builders <BUILDERS>`)
- provide other arguments as desired/necessary

Option 2 (last builder used):
- the tool will grab the last executed build command from `build/build-local.ninja`
- provide the project's root path via the command line (`-r <PATH>`)
- provide other arguments as desired/necessary, but no `--builders`!


### Use case 1 (out-of-tree Ariel OS project root)

Installation + Setup:

- see section [Installation](https://github.com/Nerving/ArielOSBOM#installation)

- have your own project [set up from a template repository](https://ariel-os.github.io/ariel-os/dev/docs/book/getting-started.html#starting-an-application-project-from-a-template-repository)

Execution:

- Run ArielOSBOM (where its repo was cloned to) with your project root path and your desired builders as cli arguments.

        cargo run -- -r <PATH_TO_PROJECT_ROOT> [--builders <BUILDER1> <BUILDER2> ...]

- The output file will be put into the the ./output directory.

### Use case 2 (Ariel OS Coap Test, non-project-root)

Installation + Setup:

- as before

- ~~Have your own project set up from a template repository~~ Clone the ArielOS main repo:

`git clone https://github.com/ariel-os/ariel-os.git`

Execution:

- Run ArielOSBOM (where its repo was cloned to) with Ariel OS repo's root path, the relative path to the test case's Cargo.toml, because it is not in the root directory, and your desired builders as cli arguments. Since we are in the original ArielOS repository, we do not have an import, so we only have the lock file at the root:

        cargo run -- -r <PATH_TO_MAINREPO_ROOT> -m ./tests/coap/Cargo.toml --import-path ./ [--builders <BUILDER1> <BUILDER2> ...]

### CLI guide

```
    -r, --root-path <PATH>
        Path to project root
        
        [default: ./]

    -b, --bom-formats <BOM_FORMAT>...
            BOM formats to generate (space separated)
            Possible values (case-insensitive):
                - raw:			            output of the raw aggregated information
                - spdx:			            no SPDX support currently
                - cdx_1.6/cyclonedx_1.6:	CycloneDX version 1.6
                - cdx_1.7/cyclonedx_1.7:    CycloneDX version 1.7
            
            [default: raw]

    -f, --file-format <FILE_EXTENSION>
            File format of the generated SBOM
            Possible values (case-insensitive):
                -json
            
            [default: json]

        --builders <BUILDERS>
            Laze builder targets (max 16, space separated) to generate SBOMs for; if not provided, uses last build command

            [default: none]

    -o, --output-name <FILE_NAME>
            File name of the generated SBOM(s)
            Depending on the builder and the SBOM format, the full file name will be <FILE_NAME>_<BUILDER>.<BOM_FORMAT>.<FILE_EXTENSION>
            
            [default: arielosbom]

        --output-directory <PATH>
            Path to where the generated SBOMs are to be stored (relative to execution path or absolute)

            [default: ./output]

    -m, --manifest-path <PATH>
            Path to the build's manifest file relative to its root
            
            [default: ./Cargo.toml]

    -l, --lock-path <PATH>
            Path to the project's lock file relative to its root
            
            [default: ./Cargo.lock]

    -i, --import-path <PATH>
            Path to the project's ArielOS import directory relative to its root
            
            [default: ./build/imports/ariel-os/]

    -h, --help
            Print help (see a summary with '-h')
```
